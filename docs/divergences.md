# Divergences and chosen readings

Every place this project had to choose a reading of IDTA 02004, IDTA
02003, IDTA 02035-2, IDTA 02006, IDTA 02023, IDTA 02002, or of the
official material, with the evidence. Non-empty on day one: the official
template (2.0.1) and the official example disagree with each other in
the ways recorded below, so a validator has to decide whom to believe
before it can report anything.

| # | observation (verified against the published files, or against the requirements indexes in `data/battery-passport/` where a row says so) | our reading |

| 18 | A `File` element's value and an OPC relationship `Target` are different kinds of string: a Target is a URI reference resolved against its source part (#13), while a File value is a part name, which ECMA-376 Part 2 defines as absolute, "/" separated, reserved characters percent-encoded, and free of empty, `.` or `..` segments. Files in the wild are not written that way. | One normaliser, two entry points. The spelling is normalised for both (the other separator, a leading `./`, a doubled separator, a step up and back, a percent escape); where the name starts from stays different. A literal match is tried before the normalised one, so an archive that really holds `%20` in an entry name keeps it — and relationship resolution lands on the entry the archive holds rather than on the normalised spelling, The two entry points ask in different orders -- the chain tries the literal first, the File rule the normalised first -- so on an archive holding two spellings of one name, or a value that is no part name at all, they can still land on different entries. Four cases were constructed and they do: a value of `../evil.step`, an archive holding both `files/x.step` and `/files/x.step`, a target resolving to a part that is absent while the File rule's normalisation finds one that is present, and an archive entry whose name ends in whitespace with a File value naming it exactly. The fourth is the sharpest and was found last: `part()` returns the entry, and `HD-D7` reports that the container holds no part at that value, because the rule folds the value before it asks and the literal match `part()` tries first therefore never sees the value the archive holds. The reader contradicting itself in one report is worse to read than either answer alone. It is still not a conformant file being refused -- an OPC part name is built from pchar and a literal space is not one, so no conformant package produces it -- which is why this stays recorded rather than repaired in a release already carrying several verdict changes. Nothing published produced any of the four. **Closed in 0.1.2 by making it one entry point rather than two**: the folding moved inside `part()`, after the literal steps instead of before them, so both callers ask in the same order and the fourth case can no longer arise. What is deliberately not folded is the archive's own entry names -- an archive holding `aasx/files/manual.pdf ` against a value of `/aasx/files/manual.pdf` stays refused, since matching it would mean supplying a character the value does not carry, and that row is in the verdict corpus to keep it that way. Measured against 0.1.1: one verdict moves, the fourth case, from `HD-D7` and exit 1 to silence and exit 0. **The grammar itself is enforced from 0.1.2 as well**: this row's own first sentence says a part name percent-encodes its reserved characters, and nothing checked, so `x?y.pdf` and `a<b>.pdf` were reported as parts the container does not hold -- sending an author to add a file that no entry can be named after -- and `[Content_Types].xml`, which OPC does not make a part at all, drew nothing. The check names the offending character and is asked only of a value a document wrote: an archive entry name is not a part name, and applying the grammar to the archive's own names took oddly spelled entries out of the canonical index and made `X4` report a part missing that was in the package. Two conservative exceptions, recorded rather than enforced: a lone `%` and any character outside ASCII. A target that is no part name at all is passed through unresolved rather than dropped: dropping it took X4's question away with it. Evidence for the strict reading: of the ten File elements in the official 02004 example, the seven that name a part all name it absolutely (two carry an empty value and one an external URL, neither of which is a part name); 02003's sample names three, also absolutely, and the official packager sidesteps escaping by substituting characters (`https___demo_com_ContactInformationAAS`) rather than encoding them. A value that is not a part name at all -- it climbs out of the package, names a directory, or carries a character no segment may hold -- is a distinct finding from a part being absent, and HD-D7 says so. **They stopped sharing a remedy in 0.1.2** and this row used to give that as the reason they are one rule: the not-a-part-name branch now carries its own, because the rule's own sentence says to add the file under the name the value gives and no entry added under `x?y.pdf` is a part. What keeps them one rule is the thing a consumer gates on -- in both, the document points at bytes this reader cannot retrieve. Whether that is still the right split is an open question and not one to settle as a side effect of improving a remedy: it would move a published rule id and the count on the front page. **0.1.4 adds the one folding this row did not have.** ECMA-376 Part 2 (5th edition, December 2021) 6.2.2.3 decides part name equivalence by ASCII case-insensitive matching — spelling the mapping out, 0x41-0x5A compared as 0x61-0x7A — and its Example 1 says a package holding `/a` cannot also hold `/A`; 7.2.5.5 maps a ZIP item to a part name with an *equivalent* prefix rather than an identical one. So `aasx/files/Manual.pdf` and a value of `/aasx/files/manual.pdf` are one name, and reporting the part absent sent an author to add a file already in the package. This is not the whitespace case above, which stays refused for the reason given there: matching that would mean supplying a character the value does not carry, while case equivalence is the standard's own statement about what two names mean. Same family as #34 and #35, which fold a boolean's case and a language tag's on the argument this row can now borrow — a finding on a conformant file is the direction with no second opinion. ASCII only: the same subclause keeps NFC/NFD collisions under *should not*, as advice to whoever writes a package, so `É` and `é` stay two names and `str.lower()` would have answered that a part is present which the archive does not hold. Asked last, after every exact spelling, so an archive holding the case the document wrote still answers with that entry; an archive holding two entries differing only in case is already outside 6.2.2.3 and resolves in the archive's own write order, pinned across twelve hash seeds. No corpus verdict moves. **The review that raised this cited "M1.12" from memory; that identifier does not appear in the 5th edition** — the M-numbered rules belong to earlier ones — **and the clause that carries the requirement is 6.2.2.3.** Right substance, wrong anchor, which is why the reading was held until the document was opened. |
